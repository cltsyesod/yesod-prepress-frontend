# CLAUDE.md

Este arquivo fornece orientações ao Claude Code (claude.ai/code) ao trabalhar com o código deste repositório.

## Visão geral

Yesod Prepress AI: um dashboard de preflight de PDF com interface em português do Brasil (pt-BR). Este repositório contém três partes:

- **Frontend** (raiz do repositório): React 19 + Vite + TypeScript + Tailwind 3 + shadcn/ui (Radix). Gerado originalmente pelo Skip; `src/components/ui/` é boilerplate do shadcn.
- **Backend** ([supabase/](supabase/)): migrations do Postgres (`migrations/0001..0009`) e Edge Functions em Deno (`start_analysis`, `start_nesting`, `start_tiling`, `analysis_callback`).
- **Analyzer** ([yesod-prepress-analyzer/](yesod-prepress-analyzer/)): serviço independente e determinístico de preflight de PDF em Python (FastAPI + Celery + Valkey), com README, Dockerfile e testes próprios. Não faz parte do build do frontend.

## Comandos

Frontend (execute na raiz do repositório; existem `package-lock.json`, `pnpm-lock.yaml` e `bun.lockb`):

- `npm run dev` / `npm start` — servidor de desenvolvimento do Vite na porta 8080
- `npm run build` — build de produção em `dist/` (`build:dev` → `dev-dist/`)
- `npm run lint` — `oxlint src` (a categoria correctness está desativada em `.oxlintrc.json`); `npm run format` / `format:check` — oxfmt
- `npm test` roda o Vitest (hoje, os testes do motor de painelamento em `src/domain/tiling/__tests__`; um teste: `npx vitest run -t "<nome>"`). Não há script separado de typecheck; use `npx tsc -p tsconfig.app.json --noEmit`.

Analyzer (a partir de `yesod-prepress-analyzer/`, conforme [.github/workflows/prepress-analyzer-ci.yml](.github/workflows/prepress-analyzer-ci.yml)): `python -m pip install -e '.[dev]'`, `ruff check app tests scripts`, `pytest --cov=app` (um único teste: `pytest tests/<arquivo>::<nome>`). Requer `qpdf` e `liblcms2` instalados. O CI só é disparado por mudanças nesse diretório.

## Arquitetura

**Pipeline de análise (abrange vários arquivos):**
1. O frontend chama a Edge Function `start_analysis` ([supabase/functions/start_analysis/index.ts](supabase/functions/start_analysis/index.ts)), que autentica o usuário, cria uma linha em `analysis_jobs` e envia um job assinado ao analyzer (`ANALYZER_URL`).
2. O analyzer baixa o PDF por uma URL assinada temporária, executa as regras e envia callbacks de progresso/conclusão assinados com HMAC para `analysis_callback`, que grava o status do job e os `analysis_issues` usando a service role.
3. O frontend acompanha o job por [src/hooks/use-analysis-job.ts](src/hooks/use-analysis-job.ts) (realtime do Supabase via `use-realtime.ts` mais polling de fallback a cada 10s). Estados finais: `completed`, `completed_with_warnings`, `failed`, `cancelled`.
4. A tela do trabalho ([src/pages/JobWorkspace.tsx](src/pages/JobWorkspace.tsx)) mostra as `analysis_issues` agrupadas por gravidade (bloqueia / precisa de decisão / informação) e grava as decisões do operador (`corrected`, `approved` com motivo = exceção aceita, `rejected` = devolver ao cliente, `ignored`).

**Arte em imagem:** o envio aceita PDF, TIFF, JPEG e PNG até 50 MB (limite por arquivo do plano gratuito da Supabase, também nos buckets). Imagem entra pela correção `image_to_pdf` ([image_pdf.py](yesod-prepress-analyzer/app/fixes/image_pdf.py)): JPEG byte a byte, TIFF/PNG sem perda, ICC e transparência mantidos; o tamanho vem da resolução gravada (sem ela, 1 px = 1 pt e a ficha/escala define o tamanho final). O analisador confere o tipo real pelo conteúdo. Análises e exportações de painéis gravam `metrics` (tempo por etapa, tamanhos, pico de memória); `scripts/benchmark_mvp.py` mede o analisador com arquivos sintéticos até 50 MB.

**Correções automáticas:** as regras do analyzer anexam `fix` à ocorrência (`analysis_issues.fix`: `target` `pdf` ou `ticket`). Correções `ticket` (ex.: escala) só alteram a ficha e reanalisam. Correções `pdf` (`upscale_images`, `set_page_boxes`, `convert_magenta_die_line`, `add_contour_cut`, `add_cut_contour`, `add_crop_marks`, em [app/fixes/engine.py](yesod-prepress-analyzer/app/fixes/engine.py); a lista também fica em `FIX_IDS` de `start_analysis`) chamam `start_analysis` com `fixes` e sem `jobId`: a Edge Function cria a cópia em `project_files` (`status = 'pending'`, `derived_from` = original) e o job; o analyzer corrige, envia a cópia por URL de upload assinada e analisa a cópia; `analysis_callback` a promove a principal ao concluir (ou a remove se falhar). O original nunca é alterado e "Voltar ao original" só troca o `is_primary`. As correções nunca convertem cores nem movem a arte; a única que reamostra pixels é `upscale_images` (Lanczos até o ppi mínimo da ficha, no máximo 4×, mantendo espaço de cor, /Decode e transparência), pedida pelo operador. A faca pelo contorno ([app/fixes/contour.py](yesod-prepress-analyzer/app/fixes/contour.py)) é medida em blocos a 0,1 mm do tamanho final, ignora o fundo branco (salvo `whiteBackground: "keep"`), pode cortar vazados (`cutHoles`) e é gravada em curvas Bézier ([paths.py](yesod-prepress-analyzer/app/fixes/paths.py)). Linhas só de contorno em 100% magenta são detectadas como faca sem cor especial (`FINISHING_MAGENTA_DIE_LINE`).

**Montagem (nesting):** `/montagem` ([Nesting.tsx](src/pages/Nesting.tsx)) cria uma linha em `nesting_runs` (material, giro, linha de corte e os trabalhos com quantidade, escala e sangria da ficha) e chama a Edge Function `start_nesting`, que assina os PDFs e envia `POST /v1/nesting` ao analyzer. O analyzer ([app/nesting/](yesod-prepress-analyzer/app/nesting/)) lê o formato real pela faca (caminhos na separação de corte); arquivos sem faca chegam só com a arte e, com `cutLines.add`, o próprio sistema gera a faca pelo contorno da arte (renderização com fundo transparente, afastamento `offsetMm` para fora, artes a menos de `mergeMm` viram uma peça). Nada gerado pelo sistema (faca, marcas, guias) pode ficar sobre a arte; encaixa com shapely (gravidade inferior-esquerda, espaçamento exato, giro em passos definidos pelo operador; retângulos só 0°/90°), monta o PDF com cada peça como form XObject recortada na sangria e envia o resultado para `pdfs/<user>/montagens/<id>.pdf`. Os eventos voltam em `analysis_callback` com `kind: "nesting"`. Peças repetidas são ladrilhadas (a peça sozinha ou em par com ela mesma girada 180°), escolhendo o padrão que gasta menos material para aquela quantidade; peças menores ocupam antes os vãos das maiores. Páginas com TrimBox e sangria são cortadas na TrimBox (não contornadas). Com espaço 0, retângulos vizinhos compartilham a linha de corte. Marcas ([app/nesting/marks.py](yesod-prepress-analyzer/app/nesting/marks.py), `params.marks`): registro do plotter numa faixa da borda que o encaixe deixa livre, marcas de corte das peças retangulares recortadas onde encostariam em outra peça e faixa de identificação. Retalhos guardados ficam em `material_offcuts` e podem ser escolhidos como material. Em folha/chapa, o resumo traz o aproveitamento da chapa inteira e o da área usada, o retalho que sobra (`offcutMm`) e quantas cópias de cada trabalho ainda cabem (`fill`, usado pelo botão "Completar a chapa").

**Painéis (tiling):** módulo próprio em `/paineis` ([Tiling.tsx](src/pages/Tiling.tsx)). Separa ARTE (PDF imutável) → PROJETO (configuração) → GEOMETRIA (calculada) → ARQUIVOS (analyzer) → GUIA. O motor é [src/domain/tiling/](src/domain/tiling/), TypeScript puro sem React: `model.ts` (poster, grade com modo auto/custom e travas, painéis com sobreposição e área branca de colagem por borda, frestas por emenda centralizadas ou de um lado, sangria por borda externa, restrição do material), `engine.ts` (`calculateProject`: painel lógico, janela impressa = lógico + sobreposições + sangria, painel físico = impresso + área branca, vizinhos, ids L{lin}C{col}; sobreposição só onde há painel vizinho ligado), `operations.ts` (grade automática pelo material, tamanhos personalizados, sanfona com mínimo e travas, adicionar/apagar linhas, juntar/separar, ligar/desligar, aplicar a toda a grade), `validate.ts` (erros bloqueiam a exportação), `migrate.ts` (formato salvo antigo), `media.ts` (largura imprimível = mídia − margens − barra de cor; giro em pé/deitado/automático e flip-flop; distribuição na mídia com comprimento, desperdício e custo), `labels.ts` (etiqueta com variáveis, preenchida na tela; o analisador só imprime o texto) e `install.ts` (áreas da instalação com nomes livres — qualquer superfície, não só veículo — e ordem de instalação: quem fica por baixo na sobreposição vai antes; ordem manual em `sequence`, numeração opcional pela instalação). A revisão (`config.revision`, token `{rev}`) sobe ao exportar de novo um projeto alterado; `config.exportedHash` (`contentHash` em `tilingService`) indica exportação desatualizada. A tela não decide regras: só chama operações e `calculateProject`; edição manual marca a grade como `custom` e recalcular pede confirmação. Medidas em mm no tamanho final, origem no canto inferior esquerdo da TrimBox. O rascunho fica em `tiling_projects` (`config = { version: 2, project, request, marks }`; modelos em `tiling_templates`); "Exportar" chama `start_tiling` e o analyzer ([app/tiling/](yesod-prepress-analyzer/app/tiling/)) revalida o material e gera o PDF com todos os painéis (arte guardada uma vez, `/Rotate` conforme o giro na mídia), o ZIP com um PDF por painel, o manifesto CSV, o guia (visão geral A3, uma folha A3 por área quando há mais de uma, e uma folha A4 por painel em ordem de instalação). Faca opcional (`config.cut`, [cut.py](yesod-prepress-analyzer/app/tiling/cut.py)): contorno da arte medido uma vez e recortado na janela de cada painel como caminhos abertos, e/ou retângulo na borda do painel físico, na separação de corte. Nos arquivos por painel ([crop.py](yesod-prepress-analyzer/app/tiling/crop.py)) só imagens sem perda são recortadas (pixels copiados, sem reamostrar); JPEG fica inteiro byte a byte, porque decodificar e regravar mudaria a imagem e a configuração, no bucket `tiling`. Em cada painel, TrimBox = painel lógico e BleedBox = janela impressa; área branca sem tinta fora dela; marcas de corte na borda física, marcas tracejadas de início/fim da sobreposição e etiqueta ficam na margem técnica, nunca sobre a arte. A imagem de referência é só tela e guia.

**Interface:** duas telas principais. `/trabalhos` ([Queue.tsx](src/pages/Queue.tsx)) recebe o PDF + ficha do trabalho e lista os trabalhos; `/trabalhos/:id` é a tela do trabalho (PDF real num iframe com URL assinada + checklist). Além delas, só `/perfis` e `/configuracoes`. Um "trabalho" é uma linha de `projects`; [src/services/jobsService.ts](src/services/jobsService.ts) é a camada usada por essas telas e lê apenas a Supabase. Mantenha a interface enxuta: nada de dashboards, dados de demonstração ou telas que não ajudem o pré-impressor no dia a dia.

**Camadas do frontend:** `pages/` (rotas definidas em [src/App.tsx](src/App.tsx), todas atrás de `ProtectedRoute` + `Layout`, exceto `/login`) → `components/<feature>/` → `services/*Service.ts` → `lib/supabase/client.ts` (único client Supabase compartilhado). O estado de autenticação vem do `AuthProvider` em `hooks/use-auth.tsx`. Os tipos compartilhados ficam em [src/types/index.ts](src/types/index.ts). O alias de caminho `@` aponta para `src`.

**Perfis de produção ainda no navegador:** [profileService.ts](src/services/profileService.ts) usa `localStorage`; o perfil completo é enviado junto ao pedido de análise. A tabela `production_profiles` já existe na Supabase para a migração. `projectService` ainda tem fallback com `mockProjects` e só é usado pela tela de perfis.

**Variáveis de ambiente:** `VITE_SUPABASE_URL` e `VITE_SUPABASE_ANON_KEY` em `.env` / `.env.local`. Deploy na Vercel (rewrite de SPA em `vercel.json`). As Edge Functions usam `SUPABASE_URL`, `SUPABASE_SERVICE_ROLE_KEY`, `ANALYZER_URL`, `ANALYZER_INBOUND_SECRET` e `ANALYZER_CALLBACK_SECRET` (assinatura HMAC em [supabase/functions/_shared/analyzer.ts](supabase/functions/_shared/analyzer.ts)). Sem `ANALYZER_URL`, `start_analysis` marca o job como falho (`analyzer_not_configured`). `analysis_callback` é publicada com `--no-verify-jwt`. O analyzer roda na VPS Hostinger via Coolify (`docker-compose.coolify.yml`, branch `feat/backend-supabase-integration`) em `https://analyzer.yesodautomation.com.br`; [deploy/VPS.md](yesod-prepress-analyzer/deploy/VPS.md) descreve a alternativa com Caddy.

**Parâmetros de produção:** nunca fixe valores (larguras de material, espaçamentos, RIP, sangria, DPI, escala). Eles vêm do perfil de produção e da ficha técnica do trabalho (`projects.job_ticket`), definidos pelo operador; a ficha tem prioridade. O sistema é pré-RIP e independente de RIP.

## Convenções e armadilhas

- `.skip.config.json` lista arquivos (configs, lockfiles, `.env*`) marcados como proibidos para edição por IA pela ferramenta Skip; edite-os apenas quando a tarefa exigir.
- `vite-plugin-react-uid.js` só fica ativo no modo de desenvolvimento.
- Mudanças no banco vão em um novo arquivo numerado em `supabase/migrations/`; não edite migrations já aplicadas.
- O texto da UI e os termos de domínio (sangria, faca de corte, perfil de produção) estão em português; mantenha o novo texto em pt-BR.
