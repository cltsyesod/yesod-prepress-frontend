# CLAUDE.md

Este arquivo fornece orientações ao Claude Code (claude.ai/code) ao trabalhar com o código deste repositório.

## Visão geral

Yesod Prepress AI: sistema de pré-impressão (pré-RIP, independente de RIP) com interface em português do Brasil (pt-BR): preflight e correções automáticas, montagem (nesting) e painéis (tiling). Este repositório contém três partes:

- **Frontend** (raiz do repositório): React 19 + Vite + TypeScript + Tailwind 3 + shadcn/ui (Radix). `src/components/ui/` é boilerplate do shadcn.
- **Backend** ([supabase/](supabase/)): migrations do Postgres (`migrations/0001..0011`) e Edge Functions em Deno (`start_analysis`, `start_nesting`, `start_tiling`, `analysis_callback`, com código comum em `_shared/`).
- **Analyzer** ([yesod-prepress-analyzer/](yesod-prepress-analyzer/)): serviço independente e determinístico de preflight de PDF em Python (FastAPI + Celery + Valkey), com README, Dockerfile e testes próprios. Não faz parte do build do frontend.

## Comandos

Frontend (execute na raiz do repositório; existem `package-lock.json`, `pnpm-lock.yaml` e `bun.lockb`):

- `npm run dev` / `npm start` — servidor de desenvolvimento do Vite na porta 8080
- `npm run build` — build de produção em `dist/` (`build:dev` → `dev-dist/`)
- `npm run lint` — `oxlint src` (a categoria correctness está desativada em `.oxlintrc.json`); `npm run format` / `format:check` — oxfmt
- `npm test` roda o Vitest (hoje, o motor de painéis em `src/domain/tiling/__tests__` e `src/services/__tests__/tilingService.test.ts`; um teste: `npx vitest run -t "<nome>"`). Não há script separado de typecheck; use `npx tsc -p tsconfig.app.json --noEmit`.

Analyzer (a partir de `yesod-prepress-analyzer/`, conforme [.github/workflows/prepress-analyzer-ci.yml](.github/workflows/prepress-analyzer-ci.yml)): `python -m pip install -e '.[dev]'`, `ruff check app tests scripts`, `pytest --cov=app` (um único teste: `pytest tests/<arquivo>::<nome>`). Requer `qpdf` e `liblcms2` instalados. O CI só é disparado por mudanças nesse diretório. `python scripts/benchmark_mvp.py` mede conversão, análise e painéis com arquivos sintéticos até 50 MB (a análise é pulada sem `qpdf`).

## Arquitetura

**Pipeline de análise (abrange vários arquivos):**
1. O frontend chama a Edge Function `start_analysis` ([supabase/functions/start_analysis/index.ts](supabase/functions/start_analysis/index.ts)), que autentica o usuário, cria uma linha em `analysis_jobs` e envia um job assinado ao analyzer (`ANALYZER_URL`).
2. O analyzer baixa o arquivo por uma URL assinada temporária (`file.expectedMimeType`; o tipo real é conferido pelo conteúdo), executa as regras e envia callbacks de progresso/conclusão assinados com HMAC para `analysis_callback`, que grava o status do job, os `analysis_issues` e as medições (`analysis_jobs.metrics`) usando a service role.
3. O frontend acompanha o job por [src/hooks/use-analysis-job.ts](src/hooks/use-analysis-job.ts) (realtime do Supabase via `use-realtime.ts` mais polling de fallback a cada 10s). Estados finais: `completed`, `completed_with_warnings`, `failed`, `cancelled`.
4. A tela do trabalho ([src/pages/JobWorkspace.tsx](src/pages/JobWorkspace.tsx)) ocupa a tela inteira (o ``Layout`` tira margem e largura máxima): cabeçalho compacto (ficha, mensagem, reanalisar; marcas, faca, sangria, baixar, voltar ao original e arquivar no menu "⋯"), a **mesa** à esquerda, em destaque ([ArtStage.tsx](src/components/jobs/stage/ArtStage.tsx): a arte com guias e medidas reais no tamanho final por fora dela, zoom com Ctrl + roda e arrastar, tela cheia, camadas do PDF e, quando há cópia corrigida, Cliente / Lado a lado / Cortina / O que mudou; os dois arquivos são desenhados no mesmo espaço do PDF, sem arredondar, porque as correções nunca movem a arte, e "O que mudou" pinta de ciano os pixels diferentes; e só inspeção, sem alterar nada: **Estrutura** ([StructureView.tsx](src/components/jobs/stage/StructureView.tsx): lista de objetos por tipo, seleção na arte com medidas reais, ppi final, fonte e camada, e "só imagens/textos/vetores/faca") e **Camadas 3D** ([Layers3D.tsx](src/components/jobs/stage/Layers3D.tsx): as placas empilhadas em CSS 3D). As duas leem o arquivo de inspeção que o analisador gera em cada análise ([inspection.py](yesod-prepress-analyzer/app/analyzer/inspection.py), enviado para ``pdfs/<dono>/inspection/<arquivo>.pdf`` pela ``inspectionUploadUrl`` de ``start_analysis``): quatro placas por página, feitas desligando no conteúdo os outros tipos de objeto (alinhadas à página), imagens reduzidas à resolução de tela e o mapa de objetos (pdfium, caixas compostas até a página; a sangria gerada pelo sistema conta cada objeto uma vez) anexado como ``objects.json``. Falha na inspeção nunca derruba a análise), e à direita uma coluna com a ficha em edição, o andamento, a situação (`StatusHero`: bloqueado / aguarda decisão / pronto, barra com uma fatia por ponto, próximo passo e o caminho cliente → correções → produção); o raio-x em cartões (`XRayTiles`, um por seção, com o número principal e a cor da pior ocorrência pendente ou do aviso de leitura, mais o cartão "Entrega" quando há cópia corrigida); e, ao lado da pré-visualização, o detalhe (`SectionDetail`): por padrão "O que precisa de você" (`analysis_issues` por gravidade; cada uma abre "Como resolver", com as saídas de [issue-solutions.ts](src/lib/issue-solutions.ts) por código de regra: corrigir no sistema, pedir ao cliente com o texto do pedido, que entra na mensagem ao cliente, ou aceitar com motivo sugerido; o operador decide: `corrected`, `approved` com motivo = exceção aceita, `rejected` = devolver ao cliente, `ignored`), ou os fatos medidos e as ocorrências da seção clicada, ou cliente × produção (`CompareTable`). O perfil vem de `analysis_jobs.file_profile`, gerado por [file_profile.py](yesod-prepress-analyzer/app/analyzer/file_profile.py); seções e códigos de regra em [src/lib/xray.ts](src/lib/xray.ts), textos dos cartões e fatos em [src/lib/xray-facts.ts](src/lib/xray-facts.ts), componentes em `src/components/jobs/xray/`. Análises anteriores ao raio-x mostram só as ocorrências até serem refeitas.

**Arte em imagem:** o envio aceita PDF, TIFF, JPEG e PNG até 50 MB (`MAX_UPLOAD_BYTES` em [projectFilesService.ts](src/services/projectFilesService.ts); é o limite por arquivo do plano gratuito da Supabase, aplicado também nos buckets pela migration 0010). A RPC `start_analysis` só aceita PDF, então `analysisJobsService.startAnalysis` manda imagem pela correção `image_to_pdf` ([image_pdf.py](yesod-prepress-analyzer/app/fixes/image_pdf.py)), que roda antes das demais: JPEG byte a byte, TIFF/PNG sem perda, ICC e transparência mantidos; o tamanho vem da resolução gravada (sem ela, 1 px = 1 pt e a ficha/escala define o tamanho final); 16 bits por canal são gravados com 8 e isso é informado. O PDF vira o arquivo principal e a imagem fica como original (nesse caso a tela do trabalho não oferece "Voltar ao original"). Painéis só abrem arte em PDF.

**Desempenho:** análises e exportações de painéis gravam `metrics` ([app/core/metrics.py](yesod-prepress-analyzer/app/core/metrics.py): segundos por etapa, tamanhos, pico de memória do processo), mostradas por `JobMetricsLine` na tela do trabalho e na aba Exportação.

**Correções automáticas:** as regras do analyzer anexam `fix` à ocorrência (`analysis_issues.fix`: `target` `pdf` ou `ticket`). Correções `ticket` (ex.: escala) só alteram a ficha e reanalisam. Correções `pdf` (`image_to_pdf`, `upscale_images`, `set_page_boxes`, `add_bleed`, `convert_magenta_die_line`, `add_contour_cut`, `add_cut_contour`, `add_crop_marks`, em [app/fixes/engine.py](yesod-prepress-analyzer/app/fixes/engine.py); a lista também fica em `FIX_IDS` de `start_analysis`) chamam `start_analysis` com `fixes` e sem `jobId`: a Edge Function cria a cópia em `project_files` (`status = 'pending'`, `derived_from` = original) e o job; o analyzer corrige, envia a cópia por URL de upload assinada e analisa a cópia; `analysis_callback` a promove a principal ao concluir (ou a remove se falhar). O original nunca é alterado e "Voltar ao original" só troca o `is_primary`. As correções nunca convertem cores nem movem a arte. ``assign_rgb_profile`` ([rgb_profile.py](yesod-prepress-analyzer/app/fixes/rgb_profile.py)) atribui sRGB ao RGB sem perfil (vetores, imagens e degradês, inclusive em form XObjects) sem mudar os valores; só é oferecida quando o RIP converte o RGB (não em ``cmyk_only``). A sangria gerada (`add_bleed`, [bleed.py](yesod-prepress-analyzer/app/fixes/bleed.py), oferecida em `PAGE_BLEED_INSUFFICIENT` e no menu "⋯") redesenha a página como form XObject e repete a borda da arte só fora do que o arquivo já imprimia, esticando a última faixa de 0,1 mm (`stretch`) ou espelhando (`mirror`), em vetor; o operador escolhe no `BleedDialog`. Ela vem antes das marcas de corte (páginas com marcas do sistema são puladas); a única que reamostra pixels é `upscale_images` (Lanczos até o ppi mínimo da ficha, no máximo 4×, mantendo espaço de cor, /Decode e transparência), pedida pelo operador. Correções que medem o arquivo (``set_page_boxes``, ``add_bleed``, marcas, facas, ``upscale_images``) só rodam com tamanho final na ficha e sem escala pendente: a tela do trabalho bloqueia (``fixBlock`` em JobWorkspace) em vez de supor página inteira = formato final em 1:1. A faca pelo contorno ([app/fixes/contour.py](yesod-prepress-analyzer/app/fixes/contour.py)) segue a arte dentro da TrimBox quando ela existe (nunca a sangria, nem a gerada), renderiza o arquivo como está naquele ponto do pedido e é medida em blocos a 0,1 mm do tamanho final, ignora o fundo branco (salvo `whiteBackground: "keep"`), pode cortar vazados (`cutHoles`) e é gravada em curvas Bézier ([paths.py](yesod-prepress-analyzer/app/fixes/paths.py)). Linhas só de contorno em 100% magenta são detectadas como faca sem cor especial (`FINISHING_MAGENTA_DIE_LINE`).

**Montagem (nesting):** `/montagem` ([Nesting.tsx](src/pages/Nesting.tsx)) cria uma linha em `nesting_runs` (material, giro, linha de corte e os trabalhos com quantidade, escala e sangria da ficha) e chama a Edge Function `start_nesting`, que assina os PDFs e envia `POST /v1/nesting` ao analyzer. O analyzer ([app/nesting/](yesod-prepress-analyzer/app/nesting/)) lê o formato real pela faca (caminhos na separação de corte); arquivos sem faca chegam só com a arte e, com `cutLines.add`, o próprio sistema gera a faca pelo contorno da arte (renderização com fundo transparente, afastamento `offsetMm` para fora, artes a menos de `mergeMm` viram uma peça). Nada gerado pelo sistema (faca, marcas, guias) pode ficar sobre a arte; encaixa com shapely (gravidade inferior-esquerda, espaçamento exato, giro em passos definidos pelo operador; retângulos só 0°/90°), monta o PDF com cada peça como form XObject recortada na sangria e envia o resultado para `pdfs/<user>/montagens/<id>.pdf`. Os eventos voltam em `analysis_callback` com `kind: "nesting"`. Peças repetidas são ladrilhadas (a peça sozinha ou em par com ela mesma girada 180°), escolhendo o padrão que gasta menos material para aquela quantidade; peças menores ocupam antes os vãos das maiores. Páginas com TrimBox e sangria são cortadas na TrimBox (não contornadas). Com espaço 0, retângulos vizinhos compartilham a linha de corte. Marcas ([app/nesting/marks.py](yesod-prepress-analyzer/app/nesting/marks.py), `params.marks`): registro do plotter numa faixa da borda que o encaixe deixa livre, marcas de corte das peças retangulares recortadas onde encostariam em outra peça e faixa de identificação. Retalhos guardados ficam em `material_offcuts` e podem ser escolhidos como material. Em folha/chapa, o resumo traz o aproveitamento da chapa inteira e o da área usada, o retalho que sobra (`offcutMm`) e quantas cópias de cada trabalho ainda cabem (`fill`, usado pelo botão "Completar a chapa").

**Painéis (tiling):** módulo próprio em `/paineis` ([Tiling.tsx](src/pages/Tiling.tsx)). Separa ARTE (PDF imutável) → PROJETO (configuração) → GEOMETRIA (calculada) → ARQUIVOS (analyzer) → GUIA. O motor é [src/domain/tiling/](src/domain/tiling/), TypeScript puro sem React: `model.ts` (poster, grade com modo auto/custom e travas, painéis com sobreposição e área branca de colagem por borda, frestas por emenda centralizadas ou de um lado, sangria por borda externa, restrição do material), `engine.ts` (`calculateProject`: painel lógico, janela impressa = lógico + sobreposições + sangria, painel físico = impresso + área branca, vizinhos, ids L{lin}C{col}; sobreposição só onde há painel vizinho ligado), `operations.ts` (grade automática pelo material, tamanhos personalizados, sanfona com mínimo e travas, adicionar/apagar linhas, juntar/separar, ligar/desligar, aplicar a toda a grade), `validate.ts` (erros bloqueiam a exportação), `migrate.ts` (formato salvo antigo), `media.ts` (largura imprimível = mídia − margens − barra de cor; giro em pé/deitado/automático e flip-flop; distribuição na mídia com comprimento, desperdício e custo), `labels.ts` (etiqueta com variáveis, preenchida na tela, e o analisador só imprime o texto; `finishingIssues` avisa antes de exportar quando a margem técnica não comporta as marcas ou a etiqueta será encurtada) e `install.ts` (áreas da instalação com nomes livres — qualquer superfície, não só veículo — e ordem de instalação: quem fica por baixo na sobreposição vai antes; ordem manual em `sequence`, numeração opcional pela instalação). A revisão (`config.revision`, token `{rev}`) sobe ao exportar de novo um projeto alterado; `config.exportedHash` (`contentHash` em `tilingService`) indica exportação desatualizada. A tela não decide regras: só chama operações e `calculateProject`; edição manual marca a grade como `custom` e recalcular pede confirmação. Medidas em mm no tamanho final, origem no canto inferior esquerdo da TrimBox.

A tela de Painéis ocupa a largura inteira (o `Layout` tira margem e largura máxima em `/paineis`): barra de ferramentas, abas Arte/Mídia/Grade/Bordas/Instalação/Saída, prancheta com duas vistas — **Grade** ([TilingCanvas.tsx](src/components/tiling/TilingCanvas.tsx): editar, arrastar linhas, seleção por retângulo) e **Arquivos** ([PanelFilesView.tsx](src/components/tiling/PanelFilesView.tsx): cada painel separado como sai no PDF, com margem, marcas, etiqueta e faca; a prévia do contorno é aproximada, de [silhouette.ts](src/components/tiling/silhouette.ts)) —, inspetor à direita, abas Painéis/Problemas/Na mídia/Exportação e barra de status.

O rascunho fica em `tiling_projects` (`config = { version: 2, page, project, request, marks, cut, separatePanels, revision, exportedHash }`; modelos em `tiling_templates`). "Exportar" chama `start_tiling` e o analyzer ([app/tiling/](yesod-prepress-analyzer/app/tiling/)) revalida o material e gera, no bucket `tiling` (cada exportação substitui a anterior):
- o PDF com todos os painéis (arte guardada uma vez, `/Rotate` conforme o giro na mídia);
- o ZIP com um PDF por painel, o guia, o manifesto CSV e a configuração;
- o guia: visão geral A3, uma folha A3 por área quando há mais de uma e uma folha A4 por painel em ordem de instalação;
- cada painel sozinho só com `config.separatePanels` (desligado por padrão; ocupa de novo o espaço do ZIP).

Arquivo recusado pelo armazenamento (ex.: acima de 50 MB) vira aviso em vez de falhar a exportação. Faca opcional (`config.cut`, [cut.py](yesod-prepress-analyzer/app/tiling/cut.py)): contorno da arte medido uma vez e recortado na janela de cada painel (caminhos abertos ou, com `closeAtEdge`, fechados na borda do painel) e/ou retângulo na borda do painel físico, na separação de corte. Nos arquivos por painel ([crop.py](yesod-prepress-analyzer/app/tiling/crop.py)) só imagens sem perda são recortadas (pixels copiados, sem reamostrar); JPEG fica inteiro byte a byte, porque decodificar e regravar mudaria a imagem. Em cada painel, TrimBox = painel lógico e BleedBox = janela impressa; área branca sem tinta fora dela; marcas de corte na borda física, marcas tracejadas de início/fim da sobreposição, marcas de centro e etiqueta ficam na margem técnica, nunca sobre a arte (a etiqueta desvia das marcas ou é encurtada, e isso é informado). A imagem de referência é só tela e guia.

**Interface:** `/trabalhos` ([Queue.tsx](src/pages/Queue.tsx)) recebe a arte (PDF ou imagem) + ficha do trabalho e lista os trabalhos; `/trabalhos/:id` é a tela do trabalho (pré-visualização do PDF com pdf.js em [PdfPreview.tsx](src/components/jobs/PdfPreview.tsx), ou a própria imagem enquanto ela não foi convertida, + checklist); `/montagem` e `/paineis` são os módulos de nesting e tiling. Além delas, só `/perfis` e `/configuracoes`. Um "trabalho" é uma linha de `projects`; [src/services/jobsService.ts](src/services/jobsService.ts) é a camada usada por essas telas e lê apenas a Supabase. Mantenha a interface enxuta: nada de dashboards, dados de demonstração ou telas que não ajudem o pré-impressor no dia a dia.

**Camadas do frontend:** `pages/` (rotas definidas em [src/App.tsx](src/App.tsx), todas atrás de `ProtectedRoute` + `Layout`, exceto `/login`) → `components/<feature>/` → `services/*Service.ts` → `lib/supabase/client.ts` (único client Supabase compartilhado). O estado de autenticação vem do `AuthProvider` em `hooks/use-auth.tsx`. Os tipos compartilhados ficam em [src/types/index.ts](src/types/index.ts). O alias de caminho `@` aponta para `src`.

**Perfis de produção ainda no navegador:** [profileService.ts](src/services/profileService.ts) usa `localStorage`; o perfil completo é enviado junto ao pedido de análise. A tabela `production_profiles` já existe na Supabase para a migração. `projectService` ainda tem fallback com `mockProjects` e só é usado pela tela de perfis.

**Variáveis de ambiente:** `VITE_SUPABASE_URL` e `VITE_SUPABASE_ANON_KEY` em `.env` / `.env.local`. Deploy na Vercel (rewrite de SPA em `vercel.json`). As Edge Functions usam `SUPABASE_URL`, `SUPABASE_SERVICE_ROLE_KEY`, `ANALYZER_URL`, `ANALYZER_INBOUND_SECRET` e `ANALYZER_CALLBACK_SECRET` (assinatura HMAC em [supabase/functions/_shared/analyzer.ts](supabase/functions/_shared/analyzer.ts)). Sem `ANALYZER_URL`, `start_analysis` marca o job como falho (`analyzer_not_configured`). `analysis_callback` é publicada com `--no-verify-jwt`. O analyzer roda na VPS Hostinger via Coolify (`docker-compose.coolify.yml`, branch `feat/backend-supabase-integration`) em `https://analyzer.yesodautomation.com.br`; cada mudança no analyzer só vale depois do Redeploy no Coolify. [deploy/VPS.md](yesod-prepress-analyzer/deploy/VPS.md) descreve a alternativa com Caddy. O trabalho fica em `feat/backend-supabase-integration`; a produção da Vercel (`main`) está atrás desse ramo, e as telas novas só aparecem na pré-visualização do ramo. A Supabase está no plano gratuito: 50 MB por arquivo e 1 GB de armazenamento.

**Parâmetros de produção:** nunca fixe valores (larguras de material, espaçamentos, RIP, sangria, DPI, escala). Eles vêm do perfil de produção e da ficha técnica do trabalho (`projects.job_ticket`), definidos pelo operador; a ficha tem prioridade. O sistema é pré-RIP e independente de RIP.

## Convenções e armadilhas

- Mudanças no banco vão em um novo arquivo numerado em `supabase/migrations/`; não edite migrations já aplicadas.
- O texto da UI e os termos de domínio (sangria, faca de corte, perfil de produção) estão em português; mantenha o novo texto em pt-BR.
- Painéis servem para qualquer superfície (fachada, empena, parede, vitrine, veículo…): não nomeie recursos nem textos como "do veículo".
- Rodar o `pytest` dentro de `yesod-prepress-analyzer/` regrava dois arquivos versionados por engano, com nomes de operadores de PDF (`155.91 297.64 m …` e `170.08 311.81 m …`); descarte essas mudanças com `git checkout` antes de commitar.
- Edge Functions publicadas pelo MCP precisam levar também `../_shared/cors.ts` e `../_shared/analyzer.ts`; `analysis_callback` vai com `verify_jwt` desligado (a autenticação é a assinatura HMAC).
